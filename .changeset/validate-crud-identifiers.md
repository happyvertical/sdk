'@happyvertical/sql': patch

Fix SQL injection through unvalidated table and column identifiers in the CRUD methods. `validateTableName()` was applied to `delete` and `count` but not to `get`, `list`, `insert`, `update`, `upsert` or `getOrInsert`, which interpolated the table name straight into SQL — `db.list("t1 WHERE 1=1 UNION SELECT id, secret FROM t1 --", {})` executed the injected clause and returned the other table's rows. Column names taken from `Object.keys(data)` and from `conflictColumns` were interpolated with no validation anywhere. Every method that interpolates an identifier now validates it, on all five adapters and on the transaction-scoped interfaces as well as the pool-backed one. Identifiers are checked rather than quoted deliberately: the accepted shape (`[a-zA-Z_][a-zA-Z0-9_]*`) contains no character that can terminate an identifier, so quoting adds nothing to safety, while quoting a column name on PostgreSQL makes it case-sensitive and would silently change which column an existing caller addresses. A table name that is not a plain identifier — a qualified `schema.table`, a quoted name, or anything containing whitespace — is now rejected where some methods previously accepted it. The `buildWhere` operator-suffix escape hatch is unchanged and remains a documented developer-controlled trust boundary.
